# The Inventory — Specification

IBM Bob 2.0 Hackathon, Sept 25–27 2026.
Working name. Not committed — see the open question at the end.

---

## 1. The problem, precisely

**Claim:** in a codebase under agentic development, the rate of redundant implementation is no longer bounded by human memory, and nothing has replaced that bound.

Unpacked:

**The old bound was tacit.** A developer with tenure held an approximate inventory of the codebase — not precise, but enough to produce "I think we already have something for that" at the right moment. It was acquired passively through reading and reviewing, never written down, and it was the only thing preventing independent reimplementation. Code review was the backstop, and reviewers used the same tacit inventory.

**Agents have no tacit inventory and cannot acquire one.** Every session starts cold. Bob's context window is 270k tokens; a mid-size repo is millions. So discovery happens by search, and search is lexical. A capability named `fmtDt` does not match a query for "date formatter". A negative search result is indistinguishable from genuine absence, so the agent concludes the capability doesn't exist and implements it — correctly, idiomatically, with tests.

**The output passes every existing gate.** It compiles, it's covered, it's reviewed. Nothing in CI is looking for "we already had this," and the human reviewer is now facing a 40-file agent-authored diff.

**Two properties make this structural rather than untidy:**

- *It compounds.* Each redundant implementation adds noise, which degrades the next session's search, which raises the probability of the next redundant implementation. The curve bends upward with agent usage, not with team size.
- *Duplicates diverge.* Two implementations of the same behaviour drift apart. One gets a bug fix, the other doesn't. This is a defect surface that no tool currently reports, because neither implementation is wrong in isolation.

**Scope of the claim.** Duplication itself is ancient and not novel. What is novel is the removal of its only bound. Stated for a judge: *duplication used to be limited by human memory; agentic development removed the memory and kept the authoring speed.*

**Falsifiable.** If Bob's search reliably finds poorly-named existing capabilities, the problem does not exist. This is testable in an hour (§7).

## 2. Why existing tools do not catch it

This objection will arrive within thirty seconds of the pitch and the answer has to be immediate.

Clone detectors — jscpd, PMD CPD, Simian, and everything in that lineage — detect **copy-paste**: shared token sequences, syntactic overlap, structural similarity of text.

Agents do not copy-paste. They **re-derive from scratch**, in their own naming style, with their own control flow. The result is two functions with identical behaviour and near-zero token overlap.

Every tool in the existing category is structurally blind to exactly the class of duplication agentic development produces. The detection problem has changed shape: from *find copied text* to **find independently authored code with equivalent behaviour**.

## 3. What we build

Three components. Only the third is Bob-specific.

### 3.1 The capability index

A semantic inventory of what the repo can already do. For each exported function, class, type, API client, error class and test helper:

- a natural-language description of behaviour, generated by reading the code (not the name, not the docstring — both lie)
- an embedding of that description
- its location, signature, and module boundary
- a callable handle for the probe (§3.2)

Keyed on description, not identifier. That is the entire point: it retrieves `fmtDt` for the query "format a date."

### 3.2 The behavioural probe

Embedding similarity gives recall with mediocre precision. Acting on a similarity score alone is how this tool becomes dangerous — telling an agent to reuse a subtly different function introduces a defect that did not previously exist. **A false "reuse this" is worse than the duplicate it prevents.**

So similarity only nominates candidates. Confirmation is empirical: generate inputs against the shared signature, execute both functions, compare outputs. The verdict is *"identical results across 200 generated inputs,"* which is a fact rather than a score.

This keeps the core deterministic and gives the demo something a judge can verify.

### 3.3 Bob integration

Constrained by what Bob 2.0.2 hooks actually permit. Verified against documentation and third-party runtime testing; **to be re-confirmed on day one.**

| Channel | Behaviour | Our use |
|---|---|---|
| `SessionStart` | stdout becomes model context; cannot block | Inject the high-level capability map once per session. Cold-start cure. |
| `UserPromptSubmit` | stdout becomes context alongside the prompt; exit 2 blocks | **Primary channel.** Query the index against the prompt, inject matching capabilities before the agent plans. |
| MCP tool | standard, no timeout constraint | `find_existing_capability(description)` for on-demand lookup mid-task. |
| `PreToolUse` | matcher is regex on tool name; **stdout ignored**; exit 2 blocks only | Backstop. Block a `write_file` / `insert_content` that duplicates a probe-confirmed capability. Rare path. |
| `Stop` | output ignored, cannot force continuation | Unusable. |

Notes: hook timeout defaults to 10 seconds, so index queries must be local and fast; indexing itself runs out of band. Bob 2.0.2's edit tools are `write_file`, `apply_diff`, `search_and_replace`, `insert_content` — matchers must target these, not `Edit`/`Write`.

**Design consequence.** Because `PreToolUse` cannot inject, the value is delivered *before planning* via `UserPromptSubmit`, not *during execution* via interception. This is better: it shapes the plan rather than interrupting the write, and costs one query per prompt instead of one per file operation.

## 4. Is this a product or a workflow?

Worth stating plainly, because it is the weakest point of the pitch.

**Framed as interception, it is a workflow step.** A check that runs before writes. Its value appears as an absence — code that didn't get written — and absences neither demo well nor sell well. It reads as a linter, and linters are ignorable.

**Framed as an artifact, it is a product.** The repo gains a queryable inventory of its own capabilities, in plain language, continuously maintained. Humans query it ("do we have anything that does X?"). Agents receive it automatically. Reuse is one consequence of owning it; others are onboarding, dead-capability detection, and answering "what can this system actually do" without reading it.

The artifact framing is the one to build toward. The noun is the product; the interception is a feature of it.

## 5. Demo

1. **Unstaged failure.** Real repo with a genuinely obscure existing utility. Ask Bob for a feature that needs it. It searches, misses, writes its own. Show both side by side. Nothing was planted.
2. **Build the inventory live.** Subagents fan out across the repo, each mapping a module, writing partial indexes merged on completion. (See open question.)
3. **Repeat.** Fresh session, identical prompt. Bob receives the matching capability at prompt time, imports it. Net new lines: zero.
4. **The defect beat.** Two pre-existing duplicates in the repo that disagree on an edge case — one patched, one not. This is where it stops being about tidiness.
5. **The curve.** Duplicate clusters per 100 commits across a repo's history, rising.

Beat 1 is the strongest and the least controllable. Beat 4 is what makes it a correctness tool rather than a cleanliness tool.

---

## 6. Metrics

- New lines written vs. lines reused, same task, with and without the inventory
- Retrieval hit rate: how often the index surfaces a capability lexical search missed
- Probe-confirmed duplicate clusters per repo
- Divergent duplicates found — pairs that were once equivalent and no longer are
- Duplicate accumulation rate over commit history

## 7. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| **Bob's search is good enough and beat 1 doesn't happen** | Fatal | One-hour falsifier: hide a utility under an unhelpful name, ask Bob to build something needing it, observe. **Run before anything else.** |
| False "reuse this" introduces a defect | High | Probe must confirm before suggesting. Suggest, don't block, on the default path. |
| Duplication is sometimes correct (bounded contexts, deliberate decoupling) | Medium | Module-boundary awareness, even crude. Never preach DRY across a deliberate seam. |
| Reads as a linter | Medium | Lead with the artifact, not the check (§4) |
| Hook behaviour differs from documentation | Medium | MCP tool is the primary path and is standard. Hooks are the enhancement, not the foundation. |
| Embedding quality on code | Low–medium | Index generated descriptions, not raw source |
| No Bob access until day one | Medium | Engine is agent-agnostic. Build and test against a Roo/Kilo-family agent or any MCP client this week; port config on day one. |

## 9. Open question

**Is the index built ahead of time, or built live during the demo by subagents?**

*Current lean: live.*

**Preprocessed** — index built before the demo, loaded from disk. Fast, reliable, no risk of a dead minute on stage. But it looks static, hides the most interesting engineering, and leaves "parallel tasks and subagents" — a criterion the challenge names explicitly — unevidenced.

**Live** — subagents fan out during the demo, one per module or directory, each producing a partial index, merged on completion. Directly demonstrates the named criterion. Produces a genuine visual beat: *N subagents mapping this repo in front of you.* Establishes that the inventory is derived from the repo, not hand-curated, which is the whole trust argument.

Cost of live: it must complete in demo time. That constrains repo size, requires bounded concurrency, needs partial results written to disk so a straggler doesn't block, and needs a warm-cache fallback if it overruns on the day.

**Open sub-questions if live is chosen:**

- What is the largest repo that can be fully indexed inside 90 seconds, and does a repo that small still contain convincing duplication?
- Can indexing be scoped to the modules relevant to the demo prompt rather than the whole repo — live, but partial?
- Does Bob reliably parallelise subagents without manual prompting, or does the fan-out need to be orchestrated outside Bob?
- Is a hybrid acceptable: index built live on stage, with a pre-built index on disk as an invisible fallback if the live run overruns?
